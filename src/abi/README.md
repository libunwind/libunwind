ABI Baseline Files
==================

This source directory contains the ABI baseline files used to detect
incompatible ABI (application binary interface) changes in libunwind.

These files are generated using the **libabigail** ABI generic analysis and
instrumentation library tools https://sourceware.org/libabigail/

Layout
------

Baselines live in

    src/abi/<arch>/<target_os>[/<variant>]/lib<name>.abi

where `<arch>` is libunwind's own architecture name (the `$(arch)` substituted
by configure, e.g. `ppc64`, `hppa`, `x86_64`).

A few architecture names cover more than one incompatible data model, and
those get an extra `<variant>` level:

| arch    | variants            |
|---------|---------------------|
| `mips`  | `o32`, `n32`, `n64` |
| `riscv` | `32`, `64`          |
| `ppc64` | `be`, `le`          |

Endianness is not itself recorded in an abi-corpus, so as a rule the big- and
little-endian flavors of an architecture share a baseline; `mips` was checked
and its dumps are byte-identical across endianness.  `ppc64` is the exception:
glibc lays out `struct _libc_vscr`, reachable from `ucontext_t`, differently on
the two, so it gets `be` and `le` baselines.

`<target_os>` is normalized: every `linux-gnu*` target (`linux-gnueabi`,
`linux-gnueabihf`, `linux-gnuabi64`, ...) uses the plain `linux-gnu`
baselines, since the floating-point ABI is not recorded either.

The variant is computed by `configure` (`abi_variant_dir`) and by Meson
(`abi_variant`); neither the build rules nor the regeneration script hardcode
the mapping.

Checking the ABI
----------------

1. Install the **libabigail** tools, at least version 2.0.
   On Ubuntu you can use the following command
    ```
    $ sudo apt install abigail-tools
    ```
    and a similar command with other package managers or you can clone the project
    from upstream and build it yourself.

2. Configure and build libunwind
    ```
    $ mkdir build; cd build
    $ ../configure CFLAGS="-g -Og"
    $ make -j
    ```

3. Run the ABI checks
    ```
    $ make -C src abi-check
    ```
    A report for each .so file will be generated into the corresponding .abidiff
    file in the build-tree's src directory.

`make check` runs `abi-check` as part of `check-local`, and `meson test` runs
the same comparisons as the tests in the `abi` suite, so ordinary test runs
catch ABI breakage too.

If an architecture has a baseline directory but a library in it has no
baseline file, the check fails.  Architectures with no baseline directory at
all (FreeBSD, HP-UX, Solaris, ...) are skipped silently.

Regenerating the baselines
--------------------------

`scripts/regen-abi-baselines` cross-compiles every architecture for which a
cross toolchain is installed and copies the resulting dumps over the
baselines:

    $ ./scripts/regen-abi-baselines               # update all baselines
    $ ./scripts/regen-abi-baselines --check       # verify without touching them
    $ ./scripts/regen-abi-baselines --target=ppc64

It expects Gentoo crossdev-style toolchain prefixes (`--list` shows them) and
reports SKIP for any target whose compiler is missing.  A single architecture
can also be regenerated by hand:

    $ make -C src lib<name>.abi
    $ cp src/lib<name>.abi "$(make -C src -s abi-targetdir)/"

Baselines are generated with `--enable-debug --enable-coredump` and
`CFLAGS="-g -Og"`, and deliberately *without* `--enable-cxx-exceptions`: the
extra `_Unwind_*` symbols that option adds are filtered out by
`cxx-exceptions.supp` instead.

Coverage gaps
-------------

- `aarch64/nto-qnx7.1.0` and `x86_64/nto-qnx7.1.0` cannot be regenerated
  without a QNX toolchain, and are stale: they still record the pre-1.10
  sonames.
- `ia64` has no baseline; no cross toolchain is readily available.
